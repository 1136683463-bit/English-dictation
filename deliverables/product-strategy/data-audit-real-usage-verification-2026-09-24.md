# 真实使用数据的独立复核（回答批六十九留下的唯一问题）

**日期**：2026-09-24
**方法**：不依赖批六十九的转述，**从原始 localStorage 重新读一遍**（含它没找到的浏览器侧）
**结论**：批六十九的结论**成立且更强**——「数据过时」这个可能**已被排除**

---

## 一、为什么要复核

批六十九（`prd-real-usage-audit-2026-09-24.md`）得出了一个重大结论：
**469 个内容单元（205 课 + 214 案 + 50 关）真实消费为 0**。
它据此把路线图**冻结**在一个未确认的前提上：

> **本批只出报告，不改代码**——所有判断都依赖「数据是否代表现状」这一个未确认前提。

它列了三种可能，并说「**问用户一句就够**」：

| 可能 | 它当时的判据 |
|---|---|
| A. 用户还没学到那一步 | `reviews: 0` ⇒ 连词汇都没开始练 |
| B. 入口不在日常路径上 | 用户可能用 dev server 用，但**没找到对应数据** |
| C. 数据是早期快照 | 装了、导了词、搁置了 |

**问题在于：这个前提不需要问用户，可以从证据判定。**
本报告把「可能 B」查到底——这是唯一没被排除的一条，因为它需要读**浏览器侧**数据，
而批六十九明确写了「我在 Chrome / Edge / Brave / Safari 的 profile 里**都没找到**」。

### 2.3 关键：批六十九说浏览器侧「都没找到」——实际**找得到**

批六十九的原话：

> 用户可能改用 dev server（`vite --host 127.0.0.1:1420`，本机确实在跑）或别的方式，
> **而我没有在浏览器 profile 里找到对应数据**（Chrome/Edge/Brave/Safari 全空）。

**复核发现：Chrome 的 `Profile 1`（不是 `Default`）里有一个 `http://127.0.0.1:1420` origin，
且它下面确实挂着 `personal-vocab-app-data-v1`。**

```
~/Library/Application Support/Google/Chrome/Profile 1/Local Storage/leveldb/016434.ldb
  offset 4578:  _http://127.0.0.1:1420 \0 adventure-auto-preload \0 …
                个人词库 key（personal-vocab-app-data-v1）就在同一段里
```

**批六十九为什么漏了**：它查的是 `Chrome/Default` + `Chrome/Profile 1` 都列了名字，
但 `016434.ldb` 里的值**是 snappy 压缩的 leveldb 块**——
`strings` 只能看到键名，看不到内容，容易判成「没有数据」。
本报告写了一个最小 snappy 解压器（leveldb 块格式）才读出来。

**读出来的内容（决定性）：**

| 字段 | 值 |
|---|---|
| `schemaVersion` | **6**（Tauri 两份都是 **8**，当前代码也是 **8**） |
| `cards` | 116（全部 `new`） |
| `reviews` | **0** |
| `units` | 6（核心100 的 Unit 1-5 + 冒险积累） |
| `adventures` | 1（The Big Race） |
| **语法相关键** | **一个都没有**（`grammarLessonsDone` / `huntResults` / `gateAttempts` **未定义**） |
| 时间戳范围 | **2026-09-10T13:58 → 14:07**（9 分钟窗口） |

**三份数据的 schemaVersion 对照（这是判新旧最可靠的尺子）：**

| 来源 | schemaVersion | 时间戳范围（北京时间） |
|---|---|---|
| Chrome dev-server | **6** | 09-10 **21:58:57 → 22:07:17**（9 分钟） |
| Tauri `cn.personal.vocab` | 8 | 09-10 **20:16:35** → 09-16 23:34:15 |
| Tauri `personal-vocab-desktop` | 8 | 09-23 02:29:01（单点，123 个字段同刻） |

⚠️ **注意一个此前没被说清的事实**：三份数据的**时间戳起点都是 09-10**
（20:16 / 21:58），也就是**这个 app 的真实使用只发生在 09-10 起**。
而**最后一条学习写入是 09-23 02:29**（`personal-vocab-desktop` 的初始化导入）。
⇒ **09-23 02:29 之后，没有任何一份存储有过学习写入。**

✅ **可验证的推论**：语法模块首次提交是 `04c5ca1`（**2026-09-12 21:52**）。
Chrome 那份停在 **09-10 22:07**，**早于语法模块存在 2 天**——
所以它「没有语法键」**不是「用户没点」，而是「那时还没有」**。
这条数据对「语法线是否被用过」**不具备证明力**（正面反面都没有）。

**但另外两份具备证明力**：schemaVersion **8**（含语法模块之后的完整结构），
时间覆盖到 **09-16** 与 **09-23**，**都晚于语法模块上线（09-12）**——
实测 `grammarLessonsDone: []`、`grammarLessonStagesDone: {}`、`huntResults: 0`。

**所以本节的真正价值是堵住一个逃生口**：「用户可能在用 dev server，只是没被找到」。
答案是：**dev-server 侧的数据确实存在，但它比 Tauri 侧更旧、且早于语法模块**，
**因此「用户悄悄在用 dev server 学语法」不成立**——
既没有那条数据，现有两份又都清楚显示语法线零使用。

### 2.4 ⚠️ 一个必须说清的时间关系：数据截止**早于**语法首屏入口上线

这是本复核里**最容易造成误判**的一点。逐条对齐时间：

| 时间（北京） | 事件 | 来源 |
|---|---|---|
| 09-10 20:16 | 最早的学习写入 | `cn.personal.vocab` 时间戳 |
| 09-12 21:52 | **语法模块首次提交**（`04c5ca1`）| git |
| 09-16 23:34 | `cn.personal.vocab` **最后一次写入** | 数据 |
| 09-23 02:29 | `personal-vocab-desktop` **最后一次学习写入** | 数据 |
| 09-23 03:05 | 单实例探针写入（非学习）| `inst-probe-ls` |
| **09-23 22:47** | **语法线首屏入口上线**（`cd92417`，今日页 Hero 主 CTA）| git |

⇒ **数据截止（09-23 02:29）比语法首屏入口上线（09-23 22:47）早 20 小时。**

**这一条对解读极其重要，两个方向的误判都要避免：**

- ❌ **不能说**「语法首屏入口上线了也没人用」——它上线时，数据已经 20 小时没动了，
  之后**没有任何一份存储被写过**，所以那份数据**根本不可能反映它的效果**。
- ✅ **只能说**「截至数据截止时，语法线零使用」。

⇒ **结论：语法现状（零使用）成立，但「首屏入口是否有效」这件事——
现有数据不能回答，因为它没覆盖到那个时点之后。**
这正是批六十九把路线图冻住的那个问题的**真实形态**：
不是「数据是不是现状」，而是「**数据停在入口上线之前，因此无法评估入口**」。

⚠️ 反过来说：**从 09-23 02:29 至今（09-24 02:00+），没有任何学习写入**。
这一条本身是硬信息——**app 在这 ~24 小时里没有被使用过**。

**所以：批六十九「问用户一句」的那个问题，答案是——「是现状」。**

### ⚠️ 但有一条数据回答不了的（必须与上面分开说）

**语法线首屏入口（`cd92417`）上线于 09-23 22:47，
而数据截止在 09-23 02:29——早 20 小时。**

| 问题 | 数据能答吗 |
|---|---|
| 「语法线此前被用过吗？」 | ✅ **能**：零使用（两份 schema 8 的数据都晚于语法模块上线）|
| 「语法首屏入口有效吗？」 | ❌ **不能**：那个入口上线时数据已停 20 小时，之后没有任何写入 |

⇒ **不要把这两件事混起来说。** 把「零使用」当成「首屏入口无效」的证据，
是**用旧数据指导新结论**——本仓库已为此设过闸（`rv18-doc-references.test.ts` 的立意）。

⚠️ **仍有的局限（诚实登记）**：
- 若用户用**别的机器、别的浏览器 profile、或没扫到的目录**，本复核看不到。

## 五之二、读数据时顺带发现的真缺陷：内置词书第 1 本装 35 条（已修）

**这一条是审计的副产品，不是原定目标**——但它比原目标更具体、可验证。

### 发现过程

复核时注意到你的数据里有个不寻常的书：「**核心100 - Unit 1 · 2**」
（描述「内置核心词第 1-20 个 · 拆分自原书」）。顺这条线查下去：

| 观察 | 实测 |
|---|---|
| `core-100-unit-1` 的卡数 | **18**（其余 Unit 2-5 各 20） |
| `unit_mtzb5ifw_gl2u1jw`（·2）的卡数 | **17** |
| 两本合计 | **35** |
| 这 17 张的前 2 张 | `construct` / `contain`——正是词表**第 19、20 个** |

### 根因（代码级）

`storage.ts` 的 `seedCoreWords`：

```ts
const unitId = seededUnits[Math.floor(index / 20)]?.id ?? seededUnits[0].id;
```

`createCoreUnits` 建 **5** 本（20×5 = 容量 **100**），
而 `core100Words` 有 **115** 条 ⇒ 索引 100-114 走 `seededUnits[5]` = `undefined`
⇒ 被 `?? seededUnits[0]` 兜回**第 1 本**。

### 空存储实测（非推断）

| 本 | 修前 | 修后 |
|---|---|---|
| `core-100-unit-1` | **35** | 20 |
| `core-100-unit-2..5` | 各 20 | 各 20 |
| `core-100-unit-6` | （不存在） | 15（描述「第 101-115 个」） |

**为什么长期没被发现**：既有测试只断言**总数**（`cards` 长度 == 词表长度），
从没断言**分布**；而 `seedWords.ts` 从**初始提交**起就是 115 条——
这个错配**从未正确过**。更有意思的是，`mg3b-backfill.test.ts` 里原本有两条用例
**在记录这个缺陷**（测试名写着「说明文案与实际条数**对不上**」、断言 `toBe(35)`）——
当时的做法（先钉住事实）是对的，只是没人把它转成修复。

### 处置

已修（提交 `2fd2daa`）：抽 `CORE_WORDS_PER_UNIT` 常量、本数由词表推导、
分本改**按名取本**（顺带修掉「删掉某本后词全体前移一位」）。
新增 3 条守门并改写那 2 条「记录缺陷」的用例为「断言正确行为」。

**对你现有数据的影响**：115 张卡不变、不新增空本、连迁 4 次稳定（幂等）。
**未追溯修复历史拆分**（`·1` + `·2` 合计 35 张）——那不是数据损坏，
是「超容被拆」的合理产物；追溯合并要动已学进度，风险高收益低。
