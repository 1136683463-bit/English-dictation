# 语法模块「练习真实摩擦」试玩协议

**目的**：验证一个核心假设——「练」段到底是**抄写**还是**检索**。

2026-09-13 的基线读数（practice 一次通过 20/20、单题 2.3–4.6 秒）有一个已知缺陷：
团队自己在 `d1-grammar-r-pilot-verdict-2026-09-13.md:54` 标注过
「打样 100% 是因为试玩者预载了答案库——不反映真实摩擦」。
所以那个读数**不能作为结论**，必须用忘掉答案的状态重测一次。

这份协议就是那次重测，约 40–60 分钟。

---

## 一、开始之前（必做）

### 1. 导出 telemetry 备份

**这一步不能跳过。** 清空学习记录会连带清掉 2026-09-13 那次 20/20 的基线证据，
那是目前唯一的历史对照数据。

打开应用 → 设置页 → 找「导出语法遥测」→ 把 JSON 存到
`deliverables/product-strategy/working/` 下，文件名带上日期（如 `telemetry-before-replay-2026-09-20.json`）。

### 2. 确认「忘掉答案」的状态

选一个满足以下任一条件的时间点：

- 距上次学这几课 ≥7 天；或
- 你确实记不清这些句子的具体措辞。

如果刚学完不久、答案还在脑子里，读出来的数字没有意义——那测的是短期记忆，不是提取难度。

### 3. 清空这几课的学习进度

设置页里清掉 L1–L4 的完成态与复习卡（具体入口以当前版本为准）。
**注意**：只清 L1–L4，不要全库清空——其他课的进度留着。

---

## 二、试玩时记录什么

做 L1、L2、L3、L4 四课，**只记「练」段（④练）**，每课 4–6 题，合计约 20 个样本。

### 记录表（复制到备忘录或用纸笔）

| 课 | 题号 | 答案 | 一次做对？ | 耗时（秒） | 用了「照着拼一遍」？ | 当时在想什么 / 在猜什么 |
|---|---|---|---|---|---|---|
| L1 | 1 | | | | | |
| L1 | 2 | | | | | |
| … | | | | | | |

三列的含义：

- **一次做对**：第一次提交就对 = 是；改过再对 = 否。**不要为了好看而改记录。**
- **耗时**：从题目出现到第一次提交，用秒表或手机计时。
- **用了「照着拼一遍」**：这个按钮本身是有用的，但用了就算「提示过」，要如实记。

**最后一列最重要**，也是这次试玩真正的价值：
n=1 的样本量下，比率数字只能看方向，但「我在猜还是在想」的主观判断非常准。
逐题问自己一句：**刚才是靠记忆拼出来的，还是靠把词块摆来摆去试出来的？**

---

## 三、做完之后怎么判读

### 三个关键读数

| 读数 | 算法 | 参照 |
|---|---|---|
| **一次通过率** | 一次做对的题数 ÷ 总题数 | 设计目标 70–85%；若 ≥95% 说明题目仍无摩擦 |
| **单题耗时中位数** | 把所有耗时排序取中间值 | 设计目标 15–30 秒；若 <5 秒说明是确认而非检索 |
| **「在猜」占比** | 主观记为「在猜」的题数 ÷ 总题数 | 若 >50%，该课要优先排查 |

### 对照修复前的数据

| 指标 | 修复前（2026-09-13） | 本次读数 | 判读 |
|---|---|---|---|
| 一次通过率 | 100%（20/20） | ______ | |
| 单题耗时 | 2.3–4.6 秒 | ______ | |
| 题量 | 20 题 | ~20 题 | |

### 按结果决定下一步

**情况 A：一次通过率 ≥95% 且中位耗时 <5 秒**

即使是清洁状态仍然秒过，说明**摩擦不来自题目难度**。按 PRD 的止损条件：

> 冻结形态改造，v2 转为纯内容重构（补核心词表、人工变式句优先）。

**情况 B：一次通过率 70–89% 且耗时 10–30 秒**

落在设计区间，说明这次补的 108 道 C 层新句起到了作用。
下一步按 PRD 走 P0-3（埋点接线），把段级退出点与单题耗时自动记下来，不再靠手工。

**情况 C：一次通过率 <70%**

太陡了——但要先分辨卡在哪一段：
若卡在**看段/跟段**（还没到练段就发懵），说明素材不够，要补例句；
若卡在**忆段**（想不起句子），那是正常提取困难，不必下调难度；
只有卡在**练段**（词都认得、就是拼不出来）才是题目的问题。

---

## 四、把结论写回哪里

做完后：

1. 把记录表与三个读数贴进 `IMPLEMENTATION_NOTES.md` 新增一节，
   **与 2026-09-13 的基线并列**（不要覆盖旧数据——那是对照组）；
2. 若某课主观「在猜」的题数超过一半，记下课号，归入下一批内容修订队列；
3. 若结论是情况 A，别急着继续改题——先按 PRD 把仪器（P0-3）装上，
   否则下一轮改动同样无法验收。

## 五、可复跑的审计脚本

本次内容修订的所有数字都能用这些脚本复现
（在项目根目录用 `node_modules/.bin/vite-node <脚本>` 执行）：

`deliverables/product-strategy/working/grammar-audit-scripts-2026-09-20/`

| 脚本 | 作用 |
|---|---|
| `g1final.ts` | G1 权威四层口径（A/B/C/D 题数与占比） |
| `dlayer.ts` | 两套 D 层口径对照（严格 vs 宽松） |
| `solvable.ts` | 题目可拼性（tokens 能否拼出答案） |
| `order.ts` | 词块是否按答案顺序给出（UI 层已打乱，非缺陷） |
| `arbitrate.ts` | 讲解厚度裁定 |
| `inventory.ts` | 全量结构盘点 |

> **口径纪律**：`g1final.ts` 是唯一权威口径，其定义是「课内词表不含 practice 自身的 tokens」。
> 换口径前先读该脚本的头部注释——为什么不能把题目的词块算作「课内出现过」。
