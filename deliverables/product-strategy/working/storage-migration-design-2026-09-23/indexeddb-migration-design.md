# 存储层迁移技术设计：localStorage → IndexedDB

**日期**：2026-09-23 · **状态**：设计（**未实施**，等决策）
**更新（第 15 轮）**：阶段 0 **已完成**，三项结论修正了本设计的两处设想：
① **多窗口一节作废**——桌面端从不创建第二个窗口，浏览器入口只是开发入口，无需 BroadcastChannel；
② **性能不是瓶颈**（14.6MB 序列化仅 18ms、写入 136ms，远低于需 Worker 的量级）；
③ **发现一个真实缺口**：未装 `single-instance`，两实例并发「读-改-写」会**丢更新**（已实测）。
详见 `IMPLEMENTATION_NOTES.md` 第 15 轮。

**更新（第 14 轮）**：阶段 0 的 SQLite 部分**已在真实桌面端跑通** ——
`tauri-plugin-sql` 可用、跨应用重启保留、中文往返一致，且 SQLite 文件位于
`~/Library/Application Support/cn.personal.vocab/`（**不在 WebView 存储目录内**），
因此「`persist()` 拿不到 → 数据可能被系统清理」这一整类问题**对 SQLite 不适用**。
同时查出一个必要修复：`sql:default` **不含写权限**，需显式加 `sql:allow-execute`。
详见 `IMPLEMENTATION_NOTES.md` 第 14 轮。
**前置结论**：第 12 轮实测「归档只能把配额墙从 8 个月推到 10 个月，
之后归档多少次都没用」——见 `IMPLEMENTATION_NOTES.md` 第 12 轮。

## 0. 一句话结论

IndexedDB 把可用容量从 **4.96 MB 提到 1000 MB（约 202 倍）**，
但**不能**用「换个 API」的方式迁移：当前「答一题同步落盘、强杀不丢」
是一条已被测试固定的保证，而 IndexedDB 只有异步 API。
所以本方案的核心不是「怎么存」，而是**「怎么在异步存储上保住那条保证」**。

**建议方案**：**双层写入**（新后端主存 + localStorage 只留最近快照做崩溃恢复），
而不是「直接替换」。它保住现有保证、可灰度、可一键回滚。

⚠️ **但后端选型已因一条实测收紧**（§7 第 6 条）：
`navigator.storage.persist()` 在 WebKit 与 Chromium 上**都返回 false**，
即 IndexedDB 处于「系统存储吃紧时**有权整体清除**」的状态，而 localStorage 不会。
**这使「直接用 IndexedDB 替换」成为一次数据安全性的降级。**
桌面端因此倾向于改用 **Tauri 原生 SQLite**（`tauri-plugin-sql` 已装），
它不受 WebView 存储清理策略影响。**这个岔路口需要先做阶段 0 验证再定。**

## 1. 前提验证（都是本机真机实测，不是推断）

### 1.1 容量与行为（Playwright 真机，WebKit + Chromium 两内核）

| 项 | localStorage | IndexedDB |
|---|---|---|
| 配额（WebKit） | **4.96 MB** | **1000 MB** |
| 配额（Chromium） | 约 10 MB | **5120 MB** |
| 写入 48 MB（含中文） | ❌ 会失败 | ✅ 往返逐字一致 |
| 写 16 MB 耗时 | — | 46 ms |
| 写 48 MB 耗时 | — | 131 ms |

**注意一个反直觉的细节**：写入 72,351,744 字符后，`storage.estimate()` 报
**144,703,488 字节 —— 正好 2.000 倍**。即：

> **「含汉字整串按 2 字节计费」是 WebKit 存储层的普遍特性，
> 不是 localStorage 专属。** 换 IndexedDB **不会**消除翻倍。

但配额大了 202 倍，这个倍数已无关紧要（本地测试用的是**纯理论字符**，
真实数据每卡 1.6 KB → 1000 MB 可容纳约 **32 万张卡**）。

### 1.2 其他能力

| 能力 | 状态 | 用途 |
|---|---|---|
| `BroadcastChannel` | ✅ 两内核可用 | 替代「字符串比对」做多窗口一致性 |
| `navigator.storage.estimate()` | ✅ 可用 | 展示真实占用（现在只能靠估算） |
| Tauri 的 IndexedDB 目录 | 存在但**为空**（从未用过） | 需真机确认持久化（见 §7 风险） |

### 1.3 迁移面的实测规模

**好消息：容量问题只涉及一个键。**

全项目共 24 个 localStorage 键，实测用户桌面上的体积：

| 键 | 体积 |
|---|---|
| `personal-vocab-app-data-v1` | **288,680 字节（唯一的大头）** |
| `adventure-telemetry-events-v1` | 6,248 |
| `settings-telemetry-events-v1` | 1,246 |
| 其余 21 个键 | 各 < 100 字节 |

也就是说**只要搬走主数据键就够了**，另外 23 个键（引导标记、tour 标记、
各种遥测与缓存）体积可忽略，**保持原样不动**可以大幅缩小改动面。

存储层的对外接口也只有 5 个函数、1 处调用点：

```
loadData()             ← AppContext.tsx:68（useState 初始化，唯一加载点）
saveData(data)         ← AppContext.tsx:203（commitData 内，唯一写入点）
readStoredSnapshot()   ← 多窗口比对 + 存储压力
parseStoredSnapshot()  ← 多窗口重放
serializeForSave()     ← 多窗口比对（惰性）
```

## 2. 核心难点：同步保证 vs 异步存储

### 2.1 难点是什么

`env2e-write-timing.test.tsx` 固定的保证：

> **学习数据（答一题 / 写一篇日记）没有 debounce 窗口，每次操作同步落盘。**
> 这意味「答题答到一半被强杀」不会丢已提交的那一题。

这条保证之所以成立，是因为 `localStorage.setItem` 是**同步**的——
`commitData` 返回时，磁盘上已经是新值。

而 IndexedDB 的写是异步的：`tx.oncomplete` 之前数据没落盘。
如果直接把 `saveData` 换成 `idbPut` 并 `await` 它，
`updateData` 就得变成 async → 78 处调用方全部要改成 `await` →
「调度答题的交互」会引入 await 边界（可能改变现有行为）。

### 2.2 为什么不能「就不管了」

有人会问：异步写也没关系，用户不会在 100 ms 内被杀进程。

**但这不成立**，原因具体：
- Tauri 桌面端用户**关窗口**就是结束进程；写队列在关闭时可能被丢弃。
- 现有的 `pagehide` / `visibilitychange` flush 兜底**无法 await**
  一次 IndexedDB 写（浏览器不给这个时机）——而 localStorage 是同步的，
  所以现在的兜底是可靠的。
- 更实际的是：**这条保证已被测试固定**，降级它是行为回归，
  不该在「换存储」这个名义下顺手丢掉。

### 2.3 解法：双层写入（hot snapshot + cold store）

```
commitData(next)
  ├─ ① localStorage.setItem(主键, 最近快照)   ← 同步，保住崩溃保证（容量小，只留"最近"）
  └─ ② void idbPut(全量数据)                   ← 异步，承担长期容量
```

**关键设计**：localStorage 不再存「全部数据」，而只存**一份最近快照**用来崩溃恢复。
它自己不需要无限增长——但我们**不能**只存摘要，否则崩溃恢复会丢数据。

那么它会不会又把 localStorage 撑满？**会**，如果什么都不做。

所以真正的方案是：**把 localStorage 降级为「崩溃恢复缓冲」，并给它一个固定预算**：

| 层 | 存什么 | 容量 | 角色 |
|---|---|---|---|
| IndexedDB | 全量 `AppData` | 1000 MB | **权威存储** |
| localStorage | 全量 `AppData` 的**最近一份** | 现有配额 | **崩溃恢复缓冲 + 降级回退** |

两层都存全量，localStorage 依然会撞 4.96 MB。**所以必须配合一步数据瘦身**：

### 2.4 配套：localStorage 层只存「恢复必需」的字段

实测 `AppData` 各字段占比（12 个月归档后）：

| 字段 | 占比 | 崩溃恢复需要吗 |
|---|---|---|
| `cards` | 35.5% | ✅ 需要（但可只留 id + status + 时间戳） |
| `reviews` | 30.1% | ❌ 不需要——丢了只影响当次会话的历史，可从 IDB 补 |
| `sentenceDetails` | 19.1% | ❌ 不需要（可从 IDB 补） |
| `schedules` | 15.2% | ✅ 需要（丢了会重排复习计划） |

**这就是本方案真正的设计点**：localStorage 只写**「进度关键字段」**
（`cards` 的进度字段 + `schedules` + 各完成态标记），数据量可压到 1/5 以下；
IndexedDB 写全量。

崩溃后恢复流程：
1. 读 localStorage 的「进度快照」→ 立即恢复进度（同步、快，无白屏）
2. 异步读 IndexedDB 全量 → 与快照比对：
   - 若 IDB 更新（快照就是它写的）→ 用 IDB 的数据补齐非关键字段
   - 若 IDB 更旧（崩溃发生在 IDB 写完成前）→ **以快照的进度为准**，
     把差量合并回 IDB（进度不回退，这是最重要的一条）

## 3. 多窗口一致性 ⚠️ **本节已作废（第 15 轮实测）**

**原设想**：R10 的合并依赖「同步读磁盘比对字符串」，异步存储下做不了，
于是改用 BroadcastChannel + `revision` 字段重做。

**实测结论：不需要**。核查三项均无：

| 检查项 | 结果 |
|---|---|
| Rust 侧是否创建窗口 | 无（只用配置声明一个 `main`） |
| 前端是否调 `WebviewWindow` / `window.open` | 无 |
| capabilities 是否授权创建窗口 | 未授权 |

**Tauri 桌面端不存在多窗口场景**；而唯一的浏览器入口
（`open-web.command`）跑的是 `npm run dev`，是**开发入口**而非产品形态
（用户在所有浏览器里都**没有**本应用数据，真实数据只在桌面端）。

因此：**`revision` 字段不必加，BroadcastChannel 不必引入。**

## 3b. ⚠️ 真正需要解决的是**单实例**（第 15 轮新增，已实测）

顺着「谁还会写这份数据」查下去，发现**未装 `single-instance` 插件**，
于是用户双击两次图标（或应用开着又从命令行启动）会得到
**两个独立进程，各持一份内存态、写同一份存储**。

实测（真起两个进程，用 SQLite 做读-改-写）：

```
实例 A：读到 n=0 → 写入 n=1；写后 n=1
实例 B：读到 n=0 → 写入 n=1；写后 n=1   ← 两次递增只生效一次，丢了一次更新
```

而本应用的核心写入（`commitData` → `saveData` **整份写**）正是这个模式。
同时确认**两个进程共享同一份 localStorage**。

**这是第 10 轮那个「多标签互相覆盖」的进程版本，而第 10 轮的合并逻辑救不了它**
（那套逻辑依赖同源 localStorage 的实时可见性，跨进程时两边各写各的）。

**建议：先修这个**——它不依赖任何迁移决策，是**当前就存在**的数据丢失路径。
修法是加 `tauri-plugin-single-instance`：第二个实例把焦点交还已有窗口后退出。

## 4. 数据模型改动 ⚠️ **已作废（第 15 轮）**

原计划加一个 `revision` 字段用于多窗口冲突判定。
因第 3 节作废（无多窗口），**本字段不需要**；单实例保证同一时刻只有一个写入方，
这比任何合并逻辑都更可靠。

（以下为原设计，保留作记录）

只加一个字段，且**不进导出/云同步的语义**：

```ts
export interface AppData {
  schemaVersion: number;
  /** R13：单调递增的写入序号，仅用于多窗口冲突判定。缺省视为 0（历史数据）。 */
  revision?: number;
  // ... 其余不变
}
```

- **不进备份**：导出时剔除（像 `apiKey` 那样脱敏），因为它是**设备内的计数器**，
  跨设备无意义；导入后从 0 起算。
- **云同步也不带**：同上。
- 这样改动面极小，且不会污染现有的导入/导出/同步契约。

## 5. 迁移与回滚

### 5.1 首次启动迁移（幂等）

```
1. 读 localStorage 主键 → 有数据？
   否 → 全新用户：直接初始化两层，结束
   是 → 继续
2. 读 IndexedDB → 有数据？
   有 → 说明已完成过迁移（或用户回滚后又前进）：
        取「两者中 revision 更大的一份」作权威，另一份覆盖
   否 → 把 localStorage 的数据完整写入 IndexedDB（保留 localStorage 原值）
3. 写一个迁移标记键（含 schemaVersion 与时间戳）
```

**幂等且有进度保护**：任一步失败都不删原数据；
下次启动重跑（因为标记没写成功）。这与现有 `loadData` 的「写不下不重置」同口径。

### 5.2 回滚

因为 localStorage **一直保留着**（只是从「权威」降为「缓冲」），
回滚只需：**关掉一个开关**（如 localStorage 里的 `storage-backend-v2: off`），
下次启动按 localStorage 走老路径。

**前提**：localStorage 缓冲必须包含「足够的进度」——
这正是 §2.4 要压的字段。

⚠️ **不可逆点**：一旦用户在新版里积累了大量数据
（IndexedDB 里 20 MB，而 localStorage 缓冲只有 2 MB），
回滚会丢掉缓冲之外的**非关键字段**（历史明细）——但**进度不丢**。
这个取舍要在界面上讲清楚（回滚是救援手段，不是常规操作）。

### 5.3 灰度

建议顺序：
1. 先只对**新用户**启用新路径（老用户不动）
2. 观察一拍（含真机 Tauri 验证）
3. 再对老用户启用，保留回滚开关一个版本周期

## 6. 存储压力提示要按层重写（否则会误报）

现状（R11）：`storageCostBytes(刚写的 JSON) > 4 MB` 就报警。

新架构下**必须改**，否则：
- 首页会一直报警（因为 localStorage 仍可能接近上限，但**那不是问题**——
  权威数据在 IndexedDB）
- 真正该报的是 **IndexedDB 接近配额**（1000 MB，几乎不会）
  或 **localStorage 缓冲写不下**（那才是真问题：丢失崩溃保护）

新的判定：

| 条件 | 含义 | 用户该做什么 |
|---|---|---|
| localStorage 缓冲写失败 | **崩溃保护失效** | 「建议导出备份」——这是真警告 |
| IndexedDB 写失败 | 主存储异常 | 同上，且重试 |
| IndexedDB 用量 > 80% | 极端长期用户 | 建议归档（现在才有意义） |

**这一条如果漏了，就是把一个已修好的产品面又搞坏**——
所以它必须和迁移同一批做，不能留到后面。

## 7. 待验证的风险（实施前必须真机确认）

| # | 风险 | 为什么是风险 | 怎么验 |
|---|---|---|---|
| 1 | **Tauri 的 IndexedDB 是否持久化** | 目录存在但**当前为空**（从未写过）。WKWebView 的 IndexedDB 在 Tauri 里是否跨启动保留，**只有真机试才知道** | 打包后写一条，重启应用读回 |
| 2 | Tauri 关闭时的写丢失窗口 | 桌面端关窗即结束进程，异步写可能未完成 | 写入后立即关窗，重启检查 |
| 3 | 隐私模式 / 存储被拒下的退化 | 现在 localStorage 被拒会走「不白屏」降级（R09 已修）；IndexedDB 被拒要有同样处理 | 模拟 `indexedDB.open` 失败 |
| 4 | 大对象写入的 UI 卡顿 | 48 MB 写 131 ms；虽然远小于 16 ms 帧预算之外，但**序列化**是同步的 | 实测 `JSON.stringify` + 写入的合计时 |
| 5 | 多窗口 + BroadcastChannel 在 Tauri 多窗口下的行为 | 浏览器验证过；Tauri 多窗口是否共享同源频道需确认 | 开两个窗口互测 |
| 6 | **配额被系统回收**（存储压力大时浏览器可清理） | IndexedDB 在存储吃紧时**可能被整体清除**，而 localStorage 不会 | ✅ **已实测：`persist()` 被拒**（见下） |

### 🔴 第 6 条已实测：`persist()` **拿不到**——这是本方案的关键障碍

真机结果（WebKit + Chromium，**两内核一致**；`file://` 与真实 http origin
两种场景**结果也一致**）：

| 读数 | WebKit | Chromium |
|---|---|---|
| `storage.persist` 可用 | ✅ | ✅ |
| `persisted()`（申请前） | **false** | **false** |
| `persist()` 返回值 | **false（未授予）** | **false（未授予）** |
| `persisted()`（申请后） | **false** | **false** |

**这意味着**：换到 IndexedDB 后，数据处于「**尽力而为（best-effort）**」状态——
当系统存储吃紧时，浏览器/WebView **有权整体清除它**，而 localStorage 没有这个语义。

> **所以：直接用 IndexedDB 替换 localStorage，是一次数据安全性上的降级，
> 而不是升级。** 容量大 202 倍，但「会不会被系统清掉」从「不会」变成「可能会」。

按标准，`persist()` 的授予通常需要「用户已安装 PWA / 已加书签 / 有高参与度信号」，
而这里两种场景都没满足，所以被拒。**这不能靠代码绕过**。

**结论：阶段 0 必须扩项**——不能只验「IndexedDB 是否持久化」，
还要回答「拿不到 persist() 时，桌面端的数据安全是否仍优于 localStorage」。

✅ **第 14 轮已给出答案**：改走 **Tauri 侧的 `tauri-plugin-sql`（SQLite）** 是可行的——
实测它在真实桌面端可用、跨重启保留，且数据库文件位于
`~/Library/Application Support/cn.personal.vocab/`，
**不在 WebView 的存储目录内**（localStorage / IndexedDB 在 `~/Library/WebKit/...`）。
所以它**天然绕开**整条第 6 条风险，而不是靠 `persist()` 去缓解。

因此：**原生 SQLite 是桌面端首选**（已实测），
IndexedDB 留给**浏览器版**（那条路径没有 SQLite）。

## 8. 工作量与建议顺序

| 阶段 | 内容 | 预估 |
|---|---|---|
| **0** | **真机验证 §7 的 6 条风险**（尤其 #1 #6） | 小，但**必须先做** |
| 1 | 抽出存储适配层（`storageBackend` 接口 + localStorage 实现），**行为零变化** | 中 |
| 2 | 加 IndexedDB 实现 + 双层写入 + 迁移 + 回滚开关 | 大 |
| 3 | 多窗口改 BroadcastChannel + `revision` 字段 | 中 |
| 4 | 存储压力提示按层重写 | 小（但漏了会回归） |
| 5 | 灰度 + 回滚演练 | 中 |

**建议**：先做阶段 0。

阶段 0 的一半结果**本轮已经拿到**，而且它指向了另一个方向：

> `persist()` **拿不到**（两内核一致），IndexedDB 处于 best-effort 状态，
> 存储吃紧时可能被系统整体清除。而 localStorage 没有这个语义。
> **→ 桌面端不宜直接用 IndexedDB 替换 localStorage。**

于是**桌面端首选改为 Tauri 原生 SQLite**（`tauri-plugin-sql` 已在 `Cargo.toml` 里，
前端尚未使用）：它是原生文件存储，容量与持久性都由应用自己控制，
天然绕开「WebView 存储可能被清」这一整类问题。

阶段 0 仍需补的验证：
1. Tauri 里 `tauri-plugin-sql` 的实际可用性（建库、读写、跨启动保留）；
2. 是否仍需前端持久层（SQLite 已足够 → 可能**不需要 IndexedDB**，方案更简单）；
3. 浏览器版（`open-web.command` 那条路径）是否保留 localStorage 作为降级。

**这个岔路口必须由验证结果决定，不能先写代码再发现。**

---

## 9. 我不建议现在做的事

- **不建议先动数据模型去瘦身字段**（第 12 轮已量化：唯一真冗余只占 8%，
  而 `createdAt`/`updatedAt` 有真实消费方）。那是「少花一点」，
  而 IndexedDB 是「根本不受限」——量级不同。
- **不建议为了省事把「同步落盘」降级**。那条保证是「强杀不丢已提交的题」，
  是这个产品的核心信任之一。
- **不建议在阶段 0 之前动任何代码**。理由见第 12 轮的教训：
  先验证前提，再动手。
