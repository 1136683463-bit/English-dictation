**批次**：第六十九批 · 2026-09-24
**方法**：直接读本机 WebKit localStorage（不是推断、不是模拟）
**结论**：**205 课语法线、214 个找错案、50 关语言之门——真实使用次数全部为 0**

## 一、数据来源（可复核）

本项目是**单人自用**，没有服务端遥测。但 Tauri 桌面端把数据写在**本机 WebKit
localStorage**，可以直接读出来——这比任何「用户研究推演」都硬。

实测找到**两份真实数据**（两个 app 标识）：

| 来源 | 路径 | 修改时间 |
|---|---|---|
| `cn.personal.vocab` | `~/Library/WebKit/cn.personal.vocab/.../localstorage.sqlite3` | 2026-09-22 |
| `personal-vocab-desktop` | `~/Library/WebKit/personal-vocab-desktop/.../localstorage.sqlite3` | 2026-09-23 |

⚠️ **读取方法**（记下来，后人可直接复用）：WebKit 的 localStorage 是 SQLite 单表
`ItemTable`，value 存为 **UTF-16LE blob**，要 `select hex(value)` 出来再
`Buffer.from(hex,"hex").toString("utf16le")` 解码。直接 `select value` 会拿到二进制。

## 三、这说明了什么

### 3.1 「做完了但没人用」比「没做完」严重得多

本会话我连续九批在**给语法线加内容与可见性**（L205 `by the time`、`quietly` 卡、
今日页主 CTA、统计页语法区块、随课词桥）。而真实数据显示：
**这条线从第一天起就没人碰过**——不是「藏得深」，是**根本没被打开过**。

我加的「今日页主 CTA」（`cd92417`）如果当时有这个数据，判断会完全不同：
- 我当时的理由：「205 课藏在导航第 4 项，内容做完了却没人看见」
- 真实情况：**不是位置问题，是这条线还不在用户的使用动线里**

### 3.2 用户实际在用的是一个**很小的闭环**

从数据看，真实使用是：
```
内置核心 100 词 → 装进 6-7 本词书 → 115 张卡（但没有一条 reviews 记录）
+ 自建冒险 6 个（玩到第 49 分钟，节点完成 0）
```
**没有复习记录**（`reviews: []`）意味着：连「卡片复习」这个核心闭环**也没跑起来**。

### 3.3 该被质疑的不是内容量，是**入口与动机**

205 课 / 214 案 / 50 关，合计 **469 个内容单元**，真实消费 **0**。
这不是「内容不够好」，而是**这 469 个单元都没有进入用户的实际动线**。

## 七、补充实测：115 张卡的精确状态（本批追加）

上文的推断「用户导了词但没开始复习」已被**精确证实**：

| 字段 | 实测值 |
|---|---|
| `cards[].status` | **115 / 115 = `"new"`** |
| `schedules[].intervalDays` | **115 / 115 = `0`** |
| `schedules[].reviewCount` | **115 / 115 = `0`** |
| `reviews` | **0 条** |
| 卡的 `sourceId` | **115 / 115 = 空**（内置卡，非用户自建）|

⇒ **用户导入了内置「核心 100 词」，但一次复习都没做过。**

### 7.1 一个看似矛盾、实为设计正确的点

115 张卡的 `nextReviewAt` 都是 `2026-09-10`（**早已过期**），但

```ts
getLearningStats(...).dueTotal  === 0
getLearningStats(...).availableNewWords === 115
```

**这不是缺陷**——`reviewService.ts:107-109` 明确写了这是 R1 的有意设计：

> 到期口径（R1）：只有已进入复习轨道的卡（learning/review）且排期已过才算"到期"。
> status === "new" 的卡不再立即到期，由每日训练队列按 New cards/day 模式通过
> `getNewCardsForToday` 混入。

**走这条路是通的**：复刻该状态实测 `getNewCardsForToday` 返回 **10 张/天**
（与 `settings.dailyNewWords: 10` 一致），115 张约 **12 天**走完。

⇒ **机制没问题，是没有人走它。**

### 7.2 冒险那 49 分钟里发生了什么（唯一的真实行为轨迹）

15 条遥测逐条还原：

| 时段 | 时长 | 行为 | 推进 |
|---|---|---|---|
| 14:45:04–14:45:41 | **32.3 秒** | 新建冒险「城市寻信」→ 进入 → 看节点 → 选一次选项 → **退出** | `nodesAdvanced: 0` |
| 15:34:02–15:34:22 | **20.4 秒** | 再次进入 → 看节点 → 选选项 → **完成 2 个节点** → 退出 | `nodesAdvanced: 2` |

两次会话合计 **53 秒**，中间隔了 **49 分钟**。
⇒ 这是**「试了一下」**的形态，不是「学习」的形态。

### 7.3 与开发时间线的对照（决定性佐证）

| 时间 | 事件 |

## 八、一个被**核实为不成立**的担忧（记录以防后人重查）

审计中发现用户 settings 里存着明文 `aiProvider.apiKey`（本地 AI 网关的 key），
我一度担心「导出备份会把密钥带出去」。

**核实结论：不会。** `exportService.ts:21-30` 已有 `withoutSecrets`：

```ts
const withoutSecrets = (data: AppData): AppData => ({
  ...data,
  settings: {
    ...data.settings,
    aiProvider: { ...data.settings.aiProvider, apiKey: REDACTED_SECRET },
    dataSync: { ...data.settings.dataSync, token: REDACTED_SECRET }
  }
});
```

实测（合成数据 + 真实 `exportJson`）：导出的 JSON 里
**既不含 `apiKey` 也不含 `dataSync.token`**。✅ 项目已正确处理。

⇒ **登记为「已核实、非缺陷」**，避免下次有人（包括我自己）重新发现同一个担忧、
再花时间查一遍。

⚠️ 顺带记一条**仍然成立**的事实：`apiKey` 在 localStorage 里是**明文**存储的。
对本地单机应用这是可接受的（数据不出本机），但若将来做多端同步，
这是需要单独评估的点。
